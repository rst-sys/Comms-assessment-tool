# Deviations from PROMPT.md

Every place the build departs from the prompt, and why. Kept current as steps land.

## Step 1 — evaluation engine

1. **No sampling temperature.** Section 5 asks for temperature 0.2 or lower. The configured model (`claude-opus-5`) rejects non-default `temperature`, `top_p` and `top_k` with a 400. The request omits them and uses `output_config.effort` (default `high`) instead. Section 12's determinism test still applies and is run by the fixture runner.

2. **Structured output plus ajv.** Section 5 says "request JSON output"; Section 6 says validate with a JSON Schema library. The engine sends the Section 6 schema as the provider's structured-output format, then validates the returned object with ajv anyway and applies the code-enforced constraints. The provider's schema subset cannot express counts, 0.5 steps or verbatim excerpts, so those are enforced in `validate.ts`.

3. **Output-structure notes appended to the system prompt.** The Section 5 prompt is sent verbatim as the first system block. A short third block (`OUTPUT_NOTES` in `prompt.ts`) states the structural conventions the schema cannot carry: ten dimensions in Section 7 order, five personas, five to twelve questions, three strongest elements and three priority improvements, `F-001` ids, verbatim excerpts, and the exact disclaimer string. The layoff block from Section 10 is inserted between them for Layoff or restructuring.

4. **Agency-scan phrases are checked for verbatim presence, like excerpts.** Section 6 requires dropping findings whose excerpt is not verbatim in the draft. The engine applies the same rule to `agency_scan.phrase`, since Section 8 highlights each phrase in the draft and a phrase that is not there cannot be highlighted. Drops are counted separately in `adjustments.dropped_scan_phrases`. Whitespace runs and quote styles are matched loosely, and the stored excerpt is always the draft's own text.

5. **Readiness override target.** When a finding needs specialist review and the model returned "Ready with minor edits", the engine sets readiness to "Escalate for senior or specialist review" and records `adjustments.readiness_overridden`. The prompt says only that the value must never be "Ready with minor edits" in that case; the escalation value was chosen because it names the reason.

6. **`context_supplied` is set in code.** The schema has the model return this flag, but the application knows whether any context field was sent. The engine overwrites the flag with the truth so the Section 7 confidence label can never be wrong, and records `adjustments.context_flag_corrected` when the model disagreed.

7. **Specialist review summary is the union.** The model's `specialist_review_summary` is merged with every type named by a kept finding, so the chips on the results page never miss a flagged review.

8. **Word-count limits are not enforced by the engine.** Section 3's 50–5,000 word range is an intake rule. The Section 12 demo drafts are under 50 words, so the engine accepts any non-empty draft and the intake screen will enforce the range.

9. **Provider-side prompt caching of the system prompt.** The system blocks carry an ephemeral cache marker so the verbatim prompt is not re-billed on every call. Only the system prompt sits before the cache breakpoint; the draft is in the user message and is never cached.

10. **No server-side refusal fallback.** The provider offers a server-side fallback that re-runs a declined request on another model. Section 4 forbids a fallback provider or a silent retry to a different model, so it is not enabled. A refusal surfaces as an `EngineError` of kind `refusal`.

11. **Credential variable name.** The SDK's default is `ANTHROPIC_API_KEY`, but hosted Claude Code environments reserve that name for the session's own account auth and refuse to set it. The engine reads `ACR_API_KEY` first and `ANTHROPIC_API_KEY` second (`resolveApiKey` in `config.ts`) and passes the value to the SDK explicitly. There is still one credential and one endpoint; this only changes where the value is read from.

12. **The watchlist, dimension definitions and calibration notes are sent to the model.** Section 5's verbatim prompt refers to "the watchlist" but never lists it; Section 8 says the watchlist is what "the model uses", and Section 7's "what it evaluates" column is the only definition of each dimension. On the first live run the model, lacking both, flagged five non-watchlist phrases on the control draft (named actors, a dated cause, a plain admission of error) and scored it 65, and assessed Demo 3's external-weather phrase as an accountability gap. The `OUTPUT_NOTES` block now carries: the six categories with their watchlist terms and typical assessments from Section 8, the rule that an external condition is never itself an accountability gap, a "never flag" list of specific actors, dated causes, admissions and concrete mechanisms, the Section 8 calibration statement (zero or one Low entry on a well-owned draft), the Section 7 dimension definitions, a note that the 3.5 ASSERTED cap applies only to the three named dimensions, a severity-proportionality rule, explicit 5.0 / 4.5 / 4.0 score bands keyed to whether a dimension's elements are present (a present element that could carry more detail is a would-raise line, not a deduction), a readiness ladder keyed to risk level with "Revise before issuing" as the floor whenever specialist review is flagged, a rule that a context field supplying a fact the draft omits turns the gap into a disclosure gap and lifts the dimension it bears on (Section 12's context-sensitivity test failed without it: the model scored Demo 1 identically with and without the known facts), a finding order (High before Moderate before Low, then a fixed dimension order) so the top findings the results page shows and Section 12's determinism test compares are stable across runs instead of following the model's arbitrary numbering, the rule that a scan phrase is the whole causal clause (so "Rapid growth brought complexity" is flagged, not "Rapid growth"), and a persona-naming convention so adverse employment drafts always carry "Affected employee" and "Remaining employee" as Section 12 expects. None of this changes the verbatim Section 5 or Section 10 text; it restates Sections 7, 8 and 12 to the model.

13. **"Growth brought complexity" is classified as Institutional abstraction.** Section 8's watchlist table lists "growth brought complexity" under External weather, but the reference example on the same page, which Section 12 makes a build test, classifies "Rapid growth brought complexity." as Institutional abstraction, High, Potential accountability gap. When the notes reproduced the table as written, the model followed it and Demo 1 failed the reference example. The notes now list the term under Institutional abstraction with the reference example's reasoning (growth and complexity are conditions of the organization, not decision-makers) and leave it out of External weather. The reference example was preferred because it is the tested behavior.

14. **The fixture runner retries a malformed response once.** The provider's structured output cannot enforce array counts (deviation 2), and in one run of about fifteen calls the model returned a persona list that failed the exactly-five check. The engine rejected it as Section 6 requires, but the runner aborted a seven-call run on that one response. `scripts/run-fixtures.ts` now makes one more call to the same model when the engine reports a validation, JSON, truncation or empty-text error, prints that it did so, and lists the retried calls in the final summary. The engine itself is unchanged: it still fails loudly and never renders a partial analysis, and the retry is same model, same endpoint, visible in the output.

15. **The determinism proxy compares dimension overlap, not exact equality.** Section 12 says the top three Demo 2 findings must be "the same in substance" across three runs. The runner's first proxy required the three top findings to cover exactly the same multiset of dimensions. Across two full runs the scores were identical (14, 15, 15 and 17, 17, 17) and the top findings said the same things, but the model sometimes split one gap into two findings (the "no actual apology" point stood alone in one run and was folded into the stakeholder-impact finding in the others), so the exact proxy failed on a difference in granularity rather than substance. The proxy now requires the distinct dimensions of each run's top three to share at least two dimensions with every other run's, and the runner still prints the three findings per run for a check by eye. The finding order rule (item 12) keeps the ranking itself stable.

16. **Two Section 12 checks are matched by substance after hand review.** On the captured run in `fixture-reports/` (46 of 48 checks passing), the two misses were matching nuances rather than engine failures. (a) Demo 2 expects a High finding for "no verification"; the engine produced that finding, with the verification dimension at 0.0, but rated it Moderate, and it does the same on Demo 1 and Demo 3. The check now accepts Moderate or higher for that one expectation. (b) Demo 3 expects the scan to flag "Macroeconomic headwinds and sector-wide conditions" as External weather, Incomplete explanation; the engine flagged both conditions with exactly that category and assessment but as two entries, "Macroeconomic headwinds" and "sector-wide conditions affected performance", because the notes ask for each watchlist phrase to be its own entry. The check now accepts either phrase. No prompt or engine change was made for these.

## Step 3 — intake screen and privacy panel

17. **Demo drafts bypass the 50-word minimum.** Section 3 sets a 50–5,000 word range for the draft; the Section 12 demo drafts are about thirty words and the demo loader must be able to evaluate them. The Evaluate button enforces the range for pasted and imported text, and for a draft loaded by the demo loader requires only that it is non-empty and under the maximum. Editing a demo draft makes it an ordinary draft again.

18. **URL import requires about forty words of article text.** Section 3 says to return the plain error for paywalled, login-gated, PDF and script-only pages. The extractor treats a page as unreadable when Readability finds no article or the article has fewer than forty words, which is how those cases present. Non-HTML responses (PDF) are unreadable by definition. Private, loopback and link-local addresses are refused before any fetch.

19. **The confidentiality notice shows once per page load.** Section 4 says "shown once on first load, dismissable". Remembering a dismissal would need browser storage, which Section 4 forbids for draft text and which the build avoids entirely, so the notice appears at the start of every page load and is dismissed with one click.

20. **Stub pages and navigation are part of this step.** Section 1 asks for a nav entry and a one-paragraph page for each stubbed area but assigns them to no build step. They ship with the app shell here, as plain text with no forms, tables or toggles. Navigation is component state, not the URL, so nothing about the review reaches the address bar or history.

## Step 4 — Minimal-Risk redraft

21. **The redraft has a length budget.** Section 9 says the redraft must preserve the original's structure and tone and change only what a finding justifies. On Demo 1, whose eleven findings each ask for information the three-sentence draft lacks, the first live revisions grew to five paragraphs and 275 words. The redraft prompt now allows at most twice the original's length or the original plus 120 words, whichever is larger, works through findings from the most severe down, and records any finding it cannot resolve within that budget in the change log with an empty revision and a stated reason. The live Demo 1 revision then came in at 149 words with every finding addressed through placeholders.

22. **Placeholders are recomputed in code.** The model returns a placeholder list, but the engine replaces it with every bracketed phrase found in the revised text, in order of first appearance, so the list the user must fill is always complete.

23. **The redraft prompt is not in PROMPT.md.** Section 9 specifies the call's inputs (the original draft, the findings, the non-invention rule) but no prompt text. `REDRAFT_SYSTEM_PROMPT` in `src/engine/redraft.ts` embeds the verbatim NON-INVENTION paragraph from Section 5 and adds the minimal-change, structure-preserving, retrospective and length-budget rules above.

24. **Stray unicode escapes are decoded.** The model occasionally double-escapes a character, so a literal `\u2014` survived into one live assessment. Every string in a validated analysis is now decoded before it reaches the page.

## Step 5 — design polish

25. **Text-safe variants of the amber and sage tokens.** Section 11 says all color pairs meet WCAG AA and to test the amber on paper specifically. Measured: amber `#B8860B` on paper `#FAF8F3` is 3.07:1 and sage `#6B8F71` is 3.42:1, both below the 4.5:1 required for normal text; muted blue `#4A6FA5` is 4.82:1 and burgundy `#7A1F2B` is 9.61:1. The spec colors are kept for bars, severity squares and borders, where contrast rules for text do not apply, and text in those tones uses darker variants: amber text `#8A6508` (5.01:1), sage text `#4A6B50` (5.64:1), blue text `#3F608F`. Ink on paper is 15.05:1 and neutral slate is 7.09:1.

26. **No third-party font requests.** Section 11 names Source Serif 4 and Inter "or equivalent" with system fallbacks. The stylesheet uses those faces when installed and falls back to system serif and sans faces; it does not load fonts from a font service, so a confidential session makes no request to a third party beyond the configured provider.

27. **Print expands panels by script.** CSS cannot open a native disclosure element, so the results page opens every panel on the browser's beforeprint event and restores the previous state afterwards; the print stylesheet hides controls and breaks pages between sections.

## Preview on claude.ai

28. **A second runtime for the claude.ai page.** Section 1 fixes the technical shape as one provider called through a zero-retention API endpoint from a server. To give the user a link without hosting, `src/artifact/` builds the same app for a claude.ai page that reaches Claude through the viewer's own account (the page's `sample` capability): no API key, no server, the viewer's usage and consent. The engine's prompt, validation, scoring and redraft rules are reused unchanged; the JSON schema is placed in the prompt because that runtime has no structured-output enforcement. Import from URL is unavailable there (the page has no network) and the privacy panel states the runtime honestly. This is a preview surface; the hosted server remains the product path. Build it with `npm run build:artifact`.

## After the owner's first testing round

29. **Four product decisions recorded in PROMPT.md.** The owner asked for a shorter executive summary, a less zealous stance on naming decision-makers, no proposed rewrites, and a headline on each Devil's Advocate card. These are written into the revisions note at the top of `PROMPT.md` and into Sections 5, 6, 8 and 9; the Section 5 prompt text was edited accordingly and regenerated. Items 21–23 above (the redraft) are superseded: the redraft engine, endpoint and panel are removed, `suggested_revision`, `suggested_edit` and `suggested_sentence` are gone from the schema, and `recommended_action` now names the kind of information to add, remove or clarify. Persona cards carry a `headline`.

30. **The claude.ai page normalizes the analysis before validating.** That runtime cannot enforce the output schema at the provider, so replies sometimes carry an extra key, six personas, a paraphrased disclaimer or a score off the 0.5 grid, and were rejected with the Section 6 message. `src/engine/normalize.ts` repairs those harmless deviations (unknown keys dropped, arrays trimmed to their limits, scores rounded to 0.5, the disclaimer set to the fixed text, missing ids filled) and the strict validator still runs afterwards; missing substance still fails. The page also asks for compact JSON with at most eight findings and eight questions so long answers are not cut off, and shows a short technical detail (an error code or a validation path, never content) under any error. The hosted server path is unchanged.

31. **Summary headline and PDF export (revisions 6 and 7).** The executive summary carries a `headline` of at most twelve words. The results page has a "Save as PDF" button that builds a text-based PDF from the analysis data with jsPDF (summary, findings, scorecard, scan, Devil's Advocate, questions, principle and disclaimer), so Section 1's "export to DOCX/PDF" exclusion now covers DOCX only. On the hosted app the file downloads directly; on the claude.ai page it goes through the page's downloads permission, which asks the viewer to confirm.


32. **Audience context documents (revision 8).** Up to eight documents describing what the audience already has or will receive: supporting documents provided with the communication, earlier communications from the organization, media reports or public commentary, and other background. Each has a kind, title, description, a note on how and when the audience receives or encountered it, a reach (whole audience, part, unknown) and, for supporting documents, a same-time flag. They are read in the browser from .txt, .md or .docx (mammoth) or pasted, travel in the request as `audience_documents`, appear in the user message as labeled blocks, and are governed by the AUDIENCE CONTEXT DOCUMENTS paragraph in the Section 5 prompt. PDF text layers are read in the browser (see item 37). On the claude.ai page the documents are trimmed, longest first, to fit that runtime's prompt size limit, and a trimmed document says so.

33. **Stance (revision 9).** `stance` (proactive or reactive) and `reacting_to` travel with the request and appear in the intake block of the user message; the Section 5 prompt gained a STANCE paragraph. Reactive requires a description of the trigger before Evaluate enables.

34. **Find public context (revision 10).** `src/engine/publicContext.ts` makes one provider call with the provider's web search tool for a topic the user typed, and returns up to six sourced items with short summaries of the material claims. The draft is never used as a query. The user chooses which items become media-report documents. The server logs a hashed request id and a result count only. The claude.ai page shows the box as unavailable. Web searches are billed by the provider in addition to tokens.

35. **Saved reviews and revision comparison (revision 12).** Section 1 stubs Compare Revisions and puts a database out of scope; this builds the comparison without one. A review is saved as a file the user keeps, so the app still stores nothing and Section 4's promise holds as written. The file carries the analysis, the settings and the context, never the draft and never a document's contents. Because the comparison only asks whether each earlier finding still applies to the NEW draft, the earlier draft is genuinely not needed.

36. **The saved file cannot be made quote-free, and says so.** The review's own prose quotes the draft: a rationale may read `The only agentive clause is "we are eliminating roles"`. Blanking the excerpt and scan-phrase fields reduces what the file carries but cannot remove quotations from the findings themselves. The tick-box is labelled as leaving out the pulled-out quotations, and a note under the save buttons states the limit plainly rather than promising more.

37. **PDF uploads and the blog post type (revision 13).** Audience context documents accept `.pdf`; the text layer is extracted in the browser with pdf.js, page by page, and the worker is a bundled same-origin asset. A PDF with no text layer (a scan or a photograph of a page) is refused with a plain message rather than silently attaching nothing, and a password-protected PDF says so. Optical character recognition is not in this build. "Blog post" is added to the Communication type list, and a blog or post URL pre-fills it on import.

38. **Type-specific protocols and the Standards Library (revision 14).** Section 1 lists Standards Library as a stub. It becomes a real page, because a tool that judges a draft against published research has to be able to show which research and where it comes from; the page is rendered from the same `src/engine/protocols.ts` objects the engine sends to the model, so it cannot claim a standard the engine does not apply. The first protocol is the structure of an effective apology from Lewicki, Polin and Lount (Negotiation and Conflict Management Research, 2016), applied when the type is Apology or the goal is to apologize or repair trust. Two design choices keep it from becoming a second scoring system: each of the six elements names the scored dimension it bears on, and the prompt states that the protocol is a lens on the ten dimensions rather than an eleventh score. The engine returns a nullable `protocol_review`; the results page, the PDF and a saved review all carry it, and Compare Revisions shows the six element by element before and after. That comparison is computed in code, not by the model — the statuses line up by name, so there is nothing to judge. The layoff protocol already in Section 10 is listed on the page too, marked as coming from the build specification rather than from published research. The stub paragraph for Standards Library is removed; the other four stubs are unchanged.

39. **A shared password and spending brakes for the hosted deployment (revision 15).** Section 1 puts authentication out of scope, and this is not it: there are no accounts, no identity, no roles and nothing stored about anyone. There is one password the owner hands to the testers. It exists because the owner asked for a public address they can share, and on a public address the owner's provider key pays for every review, so an open link is an open wallet. `src/server/access.ts` holds the gate and two daily ceilings, one per visitor and one across everyone; the paid endpoints are `/api/evaluate`, `/api/compare` and `/api/public-context`, while `/api/config` stays open so the app can decide whether to show the password screen. A visitor is counted by a hashed address kept in memory, never logged and never written down. The counters reset with the process, so `DEPLOY.md` says plainly that the real stop is the spending limit the owner sets with the provider. The session cookie is derived from the password itself, so there is no second secret to manage; holding it is equivalent to holding the password. `render.yaml` and a `Dockerfile` describe the deployment, and `tsx` moves to runtime dependencies because the start script needs it.

40. **Four features switched off for the first round of testing (revision 16).** `src/app/features.ts` is the single place that switches saving a review, comparing revisions, heightened review, audience context documents and the public-context search on or off. Four are off; heightened review stays on, because it costs almost nothing and is what makes the tool stricter on layoffs, safety and privacy, so switching it off would have had testers reviewing with a softer engine than the finished one. Each control stays visible and disabled with a "coming soon" note rather than disappearing, so a tester sees what the tool is meant to do and does not report it as a missing feature. Only two of them meaningfully reduce cost — the comparison is a second provider call and the search is an extra one — and saving a review costs nothing at all; the owner's reason was focus rather than cost, and was recorded as such. Redaction needed no switch: it was never built, and the welcome screen and privacy panel already say it is unavailable. Tests covering a switched-off feature re-enable it for their own duration, so none of the code behind these switches is left unguarded.

41. **The provider's grammar ceiling, and a schema that outgrew it.** The live deployment rejected every review with `400 … The compiled grammar is too large`. The provider compiles the structured-output schema into a grammar with a size limit, and revision 14's `protocol_review` block pushed this schema past it — the last successful live run predated that block, so the ceiling was crossed and not noticed. The fix splits one source of truth in two: `ANALYSIS_SCHEMA` stays strict and is what ajv checks every analysis against, while `relaxForProvider` derives the copy sent to the provider with every `enum` and `const` stripped at any depth. Fourteen enumerated lists, sixty-five values, were the expensive part; the structure that actually forces the shape is untouched. Deriving the copy rather than maintaining a second schema means the two cannot drift. Nothing is lost: the prompt already names the permitted values, `normalize.ts` repairs casing, and the strict validator still rejects a wrong value before anyone sees it — the same division the count, numeric and string constraints already used. `callModel` also now falls back once, dropping the format entirely and asking for the JSON in prose, if the ceiling is ever reached again; that path is not a guess, it is how the claude.ai page has always run. The rejection was invisible for an hour because the code reported the SDK's class name instead of the provider's message (item 42).

42. **Provider errors reported the class name, not the reason.** `Provider error 400: Error` was all the operator and the logs had to go on, because the handler formatted `error.name`. `providerDetail` now reads the provider's own message out of the parsed body, falling back to a flat message and then the Error's text, collapsing whitespace and capping at 300 characters. Every handler logs it. A 400 with a valid credential is nearly always a fact about the account or the request rather than a bug, so that sentence is the whole diagnosis; withholding it cost a round of guessing at credit balances and key formats that the message would have settled at once.

43. **Enum casing, and the repair the relaxed grammar made necessary (follows item 41).** With the value lists gone from the provider's copy of the schema, the first live review came back and failed strict validation. The grammar had been silently absorbing a mismatch the prompt itself creates: the system prompt writes ASSERTED and SUPPORTED in capitals for emphasis, while the schema spells them `Asserted` and `Supported`, and the specialist review types were never enumerated to the model at all. Three changes, layered. `normalize.ts` now matches every enumerated field to its permitted spelling case-insensitively — severity, claim status, dimension id, scan category and assessment, risk level, readiness, specialist review type and summary, protocol status — and leaves an unrecognized value exactly as it came so the validator still rejects it rather than this quietly inventing one. `evaluate.ts` runs that normalization on the server path, which it never did before because the grammar used to make it unnecessary; both runtimes now repair in the same place. And OUTPUT_NOTES lists every permitted value verbatim with an instruction to copy the spelling and not upper-case it for emphasis, so normalization is a net rather than a crutch. A validation failure also now names the failing path in the message, not only in the log: the path names a field and never the draft, and without it a failure is a dead end for whoever has to fix it.

44. **Latency: measurement, two levers, and an honest wait (revision 17).** The first working review took long enough that the owner called the speed unacceptable, and nothing in the build could say how long it actually took. Three changes. `callModel` now times the provider call and logs the duration with the output-token count, the effort and the speed — no content, as everywhere else — so the question is answerable from the Render log rather than by feel. `ACR_EFFORT` and a new `ACR_SPEED` are declared in `render.yaml` with what each does: effort is how deeply the engine thinks and is the larger lever, because most of a review's elapsed time is thinking rather than writing; `ACR_SPEED=fast` puts the call on the provider's fast mode, the same model at a higher output rate for roughly double the per-token price, which buys speed without reducing the depth of the review. Both are environment settings, so the owner can tune them from the dashboard without a rebuild. And the intake screen shows a progress panel while a review runs: a live elapsed count, the stage in the order the prompt asks for it, and the expected duration stated up front. It is deliberately not a real progress bar — the engine reports no progress — so it eases towards 95% and holds there rather than creeping to a fake hundred, and past about two and a half minutes it says the run is long without claiming it has failed. A button reading "Evaluating…" for ninety seconds was the whole of the previous feedback, and read as a hung page.

45. **Saying what the score could have been (revision 18).** The owner's first structured test — an AI-written good and bad draft for each of two scenarios, six identical settings, no context fields — separated good from bad by 33 and 34 points, with the two good drafts both scoring 69 and the two bad ones 36 and 35. The discrimination is the result that matters and it held across scenarios. But 69 for a draft the owner considered good reads as a harsh tool, and the reason was invisible: with no context supplied, the ASSERTED cap holds accountability_agency, causation_explanation and corrective_action_proof to 3.5 of 5, and those three carry 40 of the 100 weight, so the highest score reachable on such a run is 88, not 100. The confidence label already said the score was "on draft language only"; it did not say what that cost. The executive summary now states the cap, names the three dimensions and gives the reachable maximum, computed from the weights by `ceilingWithoutContext()` rather than written down, so it cannot drift if a weight changes. No band or weight was changed: two runs are not grounds for recalibrating a rubric, and the fix for an unexplained number is to explain it.

46. **The Standards Library cites real codes, and says where it stops (revision 20).** The owner asked for explicit reference to the standards the tool is based on, naming PRSA. The page had been built so it could only list what the engine applies, and the engine references no external code: adding "based on PRSA" would have been precisely the unsubstantiated claim the tool marks other people down for. So the page now does the honest version. Five published codes are researched and cited with links — PRSA's Code of Ethics, the Arthur W. Page Society's Page Principles, IABC's Code of Ethics for Professional Communicators, ISO 24495-1:2023 on plain language, and the Global Alliance's Melbourne Mandate — and each of the ten dimensions is mapped to the principle it rests on. The Page Principles in particular map almost one to one: tell the truth, prove it with action, listen to stakeholders and manage for tomorrow correspond to four dimensions directly. Two kinds of claim are kept apart in their own section at the top of the page: **applied**, meaning rules the engine runs, and **grounded in**, meaning codes the framework was built from that are not sent to the model and change no review. A further section states what no published code supplies and is therefore the owner's own judgment — the dimensions and weights, the score and its bands, the account, the scan, the Asserted cap, the severity thresholds — and says that disagreeing with those means disagreeing with us, not with PRSA. `src/app/standardsContent.ts` holds the codes and the mapping as data; tests assert that every dimension has at least one grounding, that no grounding cites a code the page does not list, and that the rendered page never claims to be "based on" or certified by any of them.

47. **The owner's second review of a real report (revision 21).** Five changes, all from reading an actual PDF and screenshots of the live page.

    *Language.* The Section 5 LANGUAGE rule instructed the very register the owner objected to — it literally named "a reasonable stakeholder could interpret this as" as the target phrasing. Rewritten: plain verbs, no circumlocution, and no hedging preamble on statements about what is or is not in a draft, because absence is checkable. Calibration is kept for the one case that needs it, how an audience might read a line. The owner's three successive rewrites of the same sentence are carried into the prompt as the worked example, because they define the target register better than any rule could.

    *Findings.* No text from the draft appears: not the quotation, not the flagged phrases nested under it last revision. The excerpt is still generated and still checked character-for-character against the real draft, so a finding about language that is not there is discarded before anyone reads it — the owner chose to keep that guard at the cost of a few invisible words per finding. Status dropdowns removed. Label renamed to "Ways to fix this".

    *The scan.* Its phrases leave the page entirely, on the owner's instruction: the scan still runs and still shapes what the engine finds and how it scores, but a reader who wrote the draft does not need it quoted back.

    *Devil's Advocate.* Four fields per persona become one line in the audience's own voice. The closing reporter question is fixed copy the tool never answers — a self-reflective device, not a finding.

    *Questions.* The two sections were the same list, filtered, so a reader under heightened review met some questions twice. Merged, with a review-function tag where one applies.

48. **White space: the containers were wrong, not the measure (follows item 45).** Capping running text at the measure fixed 170-character lines and created a new fault: text stopping well short inside cards that still spanned the full 1100px page, so every section had a wide empty right-hand side. Sizing the containers to the text closes it — the gap is now the card's own padding, 48px. The privacy panel moves below the executive summary rather than sitting in a sidebar, which is what forced the page that wide. Also fixes a real bug visible in the owner's screenshot: `.checkbox { display: flex }` was overriding the browser's rule for `[hidden]`, so the "keep quoted passages" tick-box rendered while saving was switched off, above a note explaining a feature that was not there.

49. **Information security added as a review function (revision 22).** The owner asked why a data-breach review never named information security, and it was not there to name: PROMPT.md Section 6 lists seven specialist review types — Legal, HR, Labor, Privacy, Investor relations, Local market, Executive — and none of them covers it. ## The protocol architecture

53. **A high-stakes event core, extracted from three drafted protocols (step 1).** The owner's library is organized by event — thirteen high-stakes events a communications team faces — with the message format and the audience asked separately, because a layoff arrives as a press release, an employee memo and a manager toolkit in the same week and needs the same accountability checks in all three. The extraction was tested against all thirteen events rather than kept on the strength of appearing in all three, and that test changed the answer: "what changes so it does not recur" fires only on events marked as a failure, because an acquisition is not a failure and a planned retirement has nothing to recur. In the shared core it would have told the author of every merger announcement to explain how they will prevent another merger. Cross-audience consistency is held back while audience documents are switched off — the tool can only compare what it is given. The file also records that an event protocol may narrow a core trigger and must say so: in a geopolitical event, vagueness about a country or the location of staff may be a safety decision the draft cannot evidence, so plain naming becomes a question there rather than a finding.

54. **`protocol_review` removed: a protocol adds instructions, never output (step 2, reverses part of item 51).** Item 51 kept the apology check in the engine after its panel came off the page, on the reasoning that the Standards Library must not cite a standard the tool does not apply. That reasoning holds; the implementation did not. The engine was writing a six-element section on every apology review that nothing displayed, and output is the expensive half of a review — the owner's own build gave the exchange rate when 748 words of removed output made reviews 26 seconds faster, about a second for every forty words. So the section goes and the protocol keeps its force: the apology block now says to raise an absent or gestural component through the ordinary findings, on the dimension already named for it, and to produce no section of its own. The Standards Library entry still describes something the tool really does. The output schema loses 1,024 characters, a fifth of it, and 883 of the characters actually sent to the provider — useful headroom, since a schema over the provider's grammar ceiling is a failure this build has already hit once. `ComparisonPanel` loses its element-by-element protocol movement, which had no data to read once the field went; Compare Revisions is switched off for this testing round in any case. Saved files written before this change still parse, because the saved-review schema does not forbid extra keys. `protocolOutput.test.ts` locks the rule in: no protocol section in the schema, no protocol naming the field, and the apology protocol still applying.

55. **An output budget: ten findings, eight questions (step 3).** PROMPT.md caps neither. Findings were uncapped entirely and real reviews of the fixtures produce six to eleven; questions were capped at twelve and every single fixture came back with eleven or twelve, which is what a ceiling set too high looks like — no ranking, just a list that stops. Left alone, each of the thirteen event protocols would have added findings and questions to every review it touched, making the wait longer and the results page longer with each one, undoing the redesign that shortened the page in the first place. The numbers live in `limits.ts` so the prompt that asks for them, the normalizer that trims an overrun and the validator that reports it cannot drift. Two rules matter more than the numbers. A protocol's questions are candidates, not obligations: the engine includes one only where the draft leaves it genuinely open, so the cap fills with what this draft needs rather than with protocol boilerplate — the event core alone lists four questions and an event protocol up to six, which would have spent the whole budget before the draft was read. And the cap is enforced in code as well as asked for in the prompt, because a protocol must not be able to talk the model past it. The trim happens before anything downstream reads the findings, so a trimmed finding cannot leave an agency-scan phrase pointing at nothing or name a specialist review with no finding behind it; that ordering is the subject of its own test. Findings are already ordered High before Moderate before Low, so the trim takes the least material. `trimmed_findings` joins the validator's adjustments and is logged, because silently dropping a finding is not the same as silently dropping a question. Worth about three seconds a review today; the point is the thirteen protocols it stops from costing thirty.

56. **Communication type becomes event and format (steps 4–6, precondition).** PROMPT.md Section 3 asks one question with seventeen answers, and the list mixes two different things: "Layoff or restructuring" is an event, "Press release" is a document. The mixing is why nothing could select a protocol reliably — a layoff arrives as a press release, an employee memo and a manager toolkit in the same week and needs the same accountability checks in all three. Apology appears in neither list: it is a posture, the Goal field already carries "Apologize or repair trust", and the apology protocol now selects on that alone and can sit on top of any event. `COMMUNICATION_EVENTS` holds the owner's thirteen plus "None of these", so a product launch is not forced to claim a disaster; `FAILURE_EVENTS` marks the ten where something failed, which is what Part B of the event core keys on. Formats gain "Customer, partner or supplier notice", which breach letters had nowhere to go in, and "Crisis statement" becomes "Public statement" now the event is asked directly. 57. **Protocols become files the owner maintains (step 4).** They were code: a `promptBlock` of hand-written prose and an `applies` function, so every protocol needed a programmer. Now each is a Markdown file in `protocols/` with a YAML settings block the engine reads and prose below it for the Standards Library page. Three decisions are worth recording. **Compiled at build time, not read at runtime**, because the same engine runs in three places — the Node server, the browser bundle for the claude.ai page, and the tests — and none of them agrees on a file system while all of them can read a TypeScript module; `npm run protocols` writes `protocolLibrary.ts`, and a test fails if the committed file and the folder disagree, so a forgotten rebuild is caught here rather than by a tester. **The prompt block is generated, not written per file**, because prose written thirteen times drifts thirteen ways, and the rules that must never vary — raise findings not sections, never propose wording, never assert a legal conclusion — belong in one place where a new file cannot quietly soften them; those rules are now sent once for the whole set rather than repeated in each block, which was costing ninety words per protocol. **The checker refuses rather than warns**: a dimension that does not exist, a review type spelled `InfoSec`, seven triggers, two protocols claiming one event, a missing Source section, or a file asking for an output section all fail by name with the line number. `yaml` is a devDependency only — the parsing happens in the build script, so nothing reaches the browser.

58. **The word budget is derived from the framework, not chosen (step 4).** I set it at 900 words, then at 1,000, both guesses, and the second was over budget within an hour of being written. It is now the length of the framework itself: the protocol layer must stay shorter than the prompt it sits under. The rule is not about speed — instructions are cached and read in parallel, so a thousand words of them cost a fraction of a second where a thousand words of output cost twenty-five — it is about attention. The framework is what makes the tool's judgment its own rather than a checklist, and if the protocol layer outgrows it every review is mostly protocol whatever the draft needs. Derived rather than written down for the same reason the score ceiling is: a number picked by hand is a guess that rots. It bit immediately and usefully, forcing the restructuring protocol to be tightened by fifty words rather than the limit being raised again.

82. **A failed review says what failed, and an unusable reply costs one more call rather than the whole review.** A tester ran a good cyber-incident draft and got "Failed after 80 seconds · reference c364884e8c40". Running it again worked. Two faults, one in the diagnosis and one in the handling.

    **The screen said nothing.** The server replaced validation, invalid-JSON, truncation and no-text errors with a single sentence, so a failure was a reference number and a stopwatch, and the actual reason — already written to the service log with its JSON pointer — was somewhere the tester cannot look. The reasoning for the substitution was that the reason might quote the draft; it cannot. Every path is a JSON pointer and every fact beside it is structural ("expected exactly 5 personas, got 3", "score 3.7 is not a 0.5 step"). The engine's own message travels to the browser now, and a test asserts both halves: the field is named, and no draft text rides along.

    **The retry the tester performed by hand, the engine performs.** All four of those faults mean one thing — the provider wrote a reply the engine cannot use — and nothing about the request is wrong, so the same question asked again is very likely to work, which is exactly what happened. `evaluateDraft` now makes at most two attempts, and only for those four kinds: auth, refusals, rate limits and overload are excluded, because a second immediate call fails the same way and spends another minute of the reader's time. Two attempts, never a loop. The worst case doubles the wait, and the progress panel already says the honest thing past 144 seconds ("still running — nothing has failed").

    Not fixed, and recorded rather than guessed at: which check the 80-second failure actually tripped. It happened before the message reached the browser, and the log line is not in hand. The retry makes that class of failure invisible to a tester whether or not it recurs; if it does recur twice in a row, the screen will now name the field. The claude.ai page runs its own loop in `src/artifact/sampleApi.ts` and does not retry; the hosted app is what testers use.
